# 单页类型评分缓存修复设计

关联 PR #38。目标是在不改变评分定义、策略动作或冻结任务集合的条件下，排除任务6700搜索页的重复评分瓶颈，并交付显式FP32重评的预检证据。研究路线、训练预算、val/test划分不变，Zqqq继续统筹。

## 原因与方案

实际环境 search_results 为页面每件商品枚举所有规格组合，每次 get_reward 都重新计算与规格无关的 get_type_reward，其中包含两次 spaCy 解析。6700参考页包含10件商品、37,344个规格组合。历史离线全组合对照记录显示，单页复用类型分后每个reward及分项都一致，参考worker总耗时629秒、缓存路径约1秒。本次不把该旧计时当作新的基准测试。

采用已有已验执行wrapper的单页缓存思路，将其纳入桥接CLI的显式开关。每次search_results/item_page调用创建临时缓存，键为商品/目标对象身份，返回评分字典副本，结束或异常时恢复原函数。保留所有规格组合、其它评分项、累计顺序和购买评分；不把页面匹配分当成终局购买奖励。缓存依赖get_type_reward对固定商品和目标确定、与options无关。

直接增加超时会保留大量重复解析；改写为组合期望值公式需要更广的数学与实现对照。本次选择范围更小的复用方案。

## 接口与边界

启动桥接时显式添加 --cache-type-reward，默认关闭。health记录 type_reward_cache=page-local-v1/off。按新进程启动生效，不支持同进程多次serve后动态关闭。只支持既有单客户端HTTPServer，不能直接用于并发服务，因为包装器临时替换模块级函数。清楚记录服务源码、开关和数据fingerprint；不得悄悄重标历史运行。

## 验证与后续

五项CPU测试覆盖重复评分减少、逐页清空、输入身份分离、返回值隔离及异常恢复。实际6700原查询连续三次返回评分与观测哈希一致；另做B1单任务诊断，明确加载FP32，固定/记录后端设置，关联实际权重文件SHA与训练endpoint张量摘要。手动动作和单任务诊断均不补入旧159项结果。
